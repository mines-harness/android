## Différences entre fournisseurs

Ces déclarations ont été lues dans les adaptateurs. Elles ne certifient pas la version installée sur un hôte : son descripteur de capacités reste la référence.

| Fournisseur                  | Déclaration des sources                                                                                                                                                                             | Conséquence mobile                                                                |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Codex                        | Steering/interruption ; approbations commande/lecture/modification avec callbacks live.                                                                                                             | Réponses seulement pour la demande active, sous les droits requis.                |
| Claude                       | Steering/interruption ; approbations commande/lecture/modification live.                                                                                                                            | Même contrôle de validité ; options propres à l’adaptateur.                       |
| Cursor                       | Streaming assistant/raisonnement/outils/plans ; pas d’approbations commande/lecture/modification/apply-patch ni questions structurées déclarées ; pas d’identifiants natifs de sous-agents exposés. | Ne pas promettre les mêmes cartes de contrôle que Codex/Claude.                   |
| OpenCode                     | Approbations live avec identifiants natifs, questions structurées et identifiants de conversations de sous-agents ; steering propre à l’adaptateur.                                                 | Le suivi et les réponses utilisent ses identifiants/capacités.                    |
| Grok                         | Modes `approval-required`, `auto`, `full-access` ; pas de mode distinct auto-accept-edits au lancement.                                                                                             | Options issues de son catalogue effectif.                                         |
| ACP / registre / Antigravity | ACP générique : approbations live, sans approbation apply-patch ni identifiants natifs de requêtes ; sous-agents natifs non génériques. Les adaptateurs peuvent préciser ces capacités.             | Aucun support universel déduit d’ACP ; modèles indisponibles visibles comme tels. |

## Ce que le CLI a permis de vérifier

Les commandes humaines inspectées couvrent `start/serve`, compte, pairing/auth, devices list/check, projets et thread list/start/send/show. Le runtime hôte contient davantage : orchestration/délégation, requêtes humaines, pièces jointes, groupes, revues, outils navigateur/appareil et transferts. Un service publié peut être exploité sans commande humaine équivalente.

Inversement, `service install`, `update`, helpers SSH et sessions temporaires du CLI disposent de l’autorité locale du propriétaire de l’hôte. Le téléphone ne reproduit pas cette autorité. Le CLI peut créer puis révoquer une session MCP temporaire ; le mobile utilise son appairage explicite. `thread send` en CLI met en file et ne signifie pas « interrompre ». Un lancement MCP sans clé de retry ne doit pas remplacer la file mobile durable.

Les contrats de base d’orchestration et le transport peer inspectés concordent entre les deux familles de sources. L’écart sur les demandes d’appareil est traité dans l’interface, sans mise à jour imposée du VPS ni publication dans les dépôts desktop.

## Validation et prérequis restants

Le bilan [VALIDATION.md](VALIDATION.md) consigne tests/lint/typecheck, builds Android/iOS, signature de test, captures et essai protocole réel. La release doit fournir l’APK et son checksum vérifié. Le prérequis restant est un compte Mines et un appareil peer approuvé manuellement pour tester le client natif connecté. Le scénario réel complet comprend appairage humain, sélection hôte/modèle, streaming, approbation si supportée, interruption, reprise après coupure, pièce jointe et consultation d’un changement.

Aucun téléphone physique, compte authentifié ou fournisseur réel ne doit être considéré comme validé sans preuve indiquée. Aucun mock isolé ne remplace ce scénario. Les licences/outils manquants, comptes nécessaires ou actions refusées doivent être rapportés avec leur statut exact.
